Mission

Preparation

Planned Activities:

  1. Use passive devices to detect remote host information.
  2. Use scripts developed by members to scan remote hosts and detect scans on local hosts.
  3. Use publicly available packages in scans on remote networks.
  4. Attempt to perform an FTP bounce scan to scan remote hosts with no detection.
  5. Employ banner scans as a last resort for otherwise unattainable information.

Software Used:

  • Siphon: Passively determine host information by fingerprinting IP packets sent by the host.
  • Fragroute: Fragment all egress traffic from our IP address.
  • LaBrea: Virtual machine designed to accept TCP connections on specific IP addresses.
  • Nmap: Used in developed scripts and independently for various scans
  • RING: Actively scans remote host and determines OS information.
  • xProbe2: Actively scans remote host and determines OS information.
  • ippacket: Library used to inject custom IP packets into network.
  • telnet: Used to connect to remote machines for banner scans.

Additional Software Produced for Exercise:

  • Script written by fiiiffffth:
    After some research with LaBrea, Qian developed a script with a 3-packet algorithm for determining whether a host is really up, the results of which may also aid in OS identification.
  • Scripts written by Redvader:
    1. "Defender"
      Detect enemy attacks that tried to map our network. The first script, called "Defender", was maintaining a list of the different IP's of the local sub-network that were scanned by a different sub-network (using ICMP or TCP packets). If the number of IP's scanned was bigger than a MAX-NUM in a certain time period TIME-MAX then, an alert was logged into a Logfile.
    2. "Attacker"
      Identifies all hosts in a given sub-network. Sends SYN packets to all 255 IP addresses on a subnetwork in a random order to one or more predefined ports that were pre-determined to have the greatest probability of being open ( 21, 80, and 139. Port 22 was used for hosts with firewalls (ie. alpha machine) ). Each packet sent contained a source IP address of a different non-existent local machine. Replies from remote hosts are counted in a scoring table. Real machines are identified by counting SYN/ACKs resulting from expiring timeouts on the remote machine.

The above scripts were developed with the following observations:

  1. IP sweeping from a range of IP addresses from different ports is not easily detectable by a standard install of Snort.
  2. Simple confusers treat requests at different ports uniformly.
  3. After receiving a SYN, simple confusers will respond with a single SYN/ACK while a normal host will keep sending SYN/ACKs multiple times until timeout.
  4. Sending a SYN to confusers causes a SYN/ACK response. With some confusers sending a subsequent ACK results in another SYN/ACK.

TCP Port Scan Group     

Goal

Scan open ports in hosts of Alpha Team

Members

    "monalisa"   Vrishali Wagle   vrishali@cs.ucsb.edu  
    "Tarantula"   Kavitha Srinivasan   kavitha@cs.ucsb.edu  
    "touchmoon"   Hangjin Zhang   hangjin@cs.ucsb.edu  

Mission

Try to find all the open ports in the Alpha Team's hosts. Meanwhile, we try the best to make our scans stealth, reduce the possibility of being detected by Alpha Team, or make IDS generates many false postive.

Preparation

We choose nmap as the basic tool. A shell script is written to carry out the scan automatically, given a list of target hosts.

Because most scan mode will be easily detected by snort,  we changed the normal usage of nmap. To somewhat "cheat" the IDS, such as snort, we use nmap with -S option, however, the source addresses used are all "virtual IP" -- none of these hosts exist in our subnet. The confuser group developed a tool to make these virtual hosts look like alive.

The current version of Snort detects only (single-single) or (single-multiple)types of portscans. To take advantage of this, "monalisa" and "Tarantula" wrote programs to scan every port from a different "virtual IP" on our subnet.This will be regarded as different clients setting connections to various ports and not as a portscan.However we come to know about the openports on those machines.

Also, In default snort.conf, the port-limit is set to 20 in 60 seconds. As a effort of reducing possibility of being dectected by snort, "touchmoon" scanned only 19 ports for every nmap run, i.e, use -p option to limit the port range from <$low>-<$low+18>.

The scanning is performed in two steps. First, we scan the well known ports that probably will be open in a default system. Then, we start another scan process trying to detect other ports.

In addition, "monalisa" and "Tarantula" had also written a script for UDP portscan on similar lines, and a portscan detector that detects precisely the kind of attack we used (portscan from multiple hosts on a single subnet) but these were not used in the actual exercise.

Execution

Right at the beginning of the exercise, "monalisa" and "Tarantula" disabled Telnet, finger and anonymous ftp on the omega machine.

During the setup of the exercise, "touchmoon" generated some files which was feed to the scan script as arguments. First is the target host list, reported by the host-info group. Second is the virtual machine list, copied from "yourbases". The scan script starts n(number of target hosts) processes to scan  hosts, 19 ports each time, using one of the virtual IP as source IP. And using another virtual IP for the next 19 ports.

"monalisa" and "Tarantula" first carried out portscan on the well-known ports on hosts reported to be alive on the alpha team subnet as well as the external subnet. Each port was scanned from a differnt virtual machine so this portscan was not detected by Snort. The result was obtained quickly and we got to know that Telnet was open on 3 outof the 4 machines on the alpha team's subnet. We then used Telnet to find the Operating systems running on those machinies to verify the results obtained by the hosts-info team. FTP servers were open too, and we established anonymous FTP connections on each of their host.

The results of the portscans are

  • Initial Scan on 192.168.11.37
  • Initial Scan on 192.168.11.56
  • Initial Scan on 192.168.11.67
  • Initial Scan on 192.168.11.81
  • Scan of first 1500 ports on 192.168.11.37
  • Scan of first 1500 ports on 192.168.11.56
  • Scan of first 1500 ports on 192.168.11.67
  • Scan of first 1500 ports on 192.168.11.81
  • Initial Scan on 192.168.3.10

Evalutation

The plan of TCP port scan was executed without a hitch. We got a lot of open ports on each targert host.

However, virtual machine mechanism does not seems to be effecient enough in brute force scan. We didn't finish scanning the entire port range. Within 2 hours, only about 20K ports are scaned for each host.

In brute force scan, maybe choosing port range randomly helps, but we did not test that.

UDP Port Scan Group     

Goal

Creation of a UDP Port Scanner that executes covert scans from the Omega Team Subnet, to collect information about the UDP ports on Alpha Team Subnet.

Members

    "joe"   Ashwin Murthy   ashwin@cs.ucsb.edu  
    "danger"   Perumal Sambasivam   peru@cs.ucsb.edu  

Mission

Setup and deployment of a UDP Scan Tool. The goal of the program was to scan a number of important ports on the alpha subnet and evade detection by any Intrusion Detection System that might have been present on that subnet. Both the team members were involved with all aspects of the mission's accomplishment.

Preparation

We basically studied the manner in which snort detects the UDP port scans. We observed that if udp scans are performed at a fast rate ( above a configurable threshold), they get detected by snort. So, our basic goal was to overcome this and bypass snort on alpha.

Initially, we attempted to do the scans using nmap. But, we soon found that nmap gets detected easily by snort since it scans ports at a very fast rate. Though it has an option where we can specify a delay, this delay is per-packet delay rather than a per-host delay, which is what we want. Hence usage of this option in nmap results in scanning of a very few ports in the given time of 2 hours.

Strategy for Stealth UDP scans

Our main strategy to avoid detection and at the same time scan as many ports as possible was to first divide the port range into two: the most common ones in [1-1500] (which is all nmap does) and the remaining ports which are less important to us. Inorder to achieve this, we first had to develop our own UDP port scan tool

The UDP port scan tool developed by us consisted of two parts. One was the packet sending module, written using libnet, other was the packet capture module, written using libpcap. The packet sending module basically sent out UDP data to the different ports on the alpha subnet. The packet capture module took care of capturing ICMP replies. The scanner tool is available here. The capture tool is here.

In order to go undetected, we basically scan multiple hosts on alpha in a cyclic manner. That is, instead of scanning all ports in one host before scanning another host, we scan one port on one host and then another port on another host etc. The source address of each scan was spoofed to be different virtual IP addresses in the omega subnet.Also, each time the ports to be scanned were randomly selected. The above two features enabled us to avoid any kind of noticable scan pattern so that we could go undetected even if the target subnet used an IDS based on these patterns rather than timers.

Execution

During the exercise, the host information team provided us with the list of IP addresses on alpha subnet. The confuser team provided us with the list of virtual ip addresses that they had created. We used these virtual addresses as spoofed source ip addresses for our udp port scans.

We first scanned the first 1500 ports (and randomly chosen in [1-1500]) in each of the 4 alpha hosts. We then repeated the same for the remaining ports in the remaining time. As the packet sender module was sending udp packets, the packet capture module was simultaneously listening to capture ICMP port unreachable messages. Its final output was a list of open ports, in each host. The list of open ports is available here.

Evalutation

From the output, we could identify a number of open ports on each of alpha's hosts. But there is also a possibility that several udp packets might have been lost (due to firewall etc.) Hence our results may show slightly more ports as being open than what may be actually true. But we believe that to large extent, the results obtained are valid.

Miscellaneous

By deafult snort detects scans on ports if the packet arrival rate is more than 20 ports per minute. We safely assumed that the alpha team would not reduce this to less than 10 ports per minute. Beacuse such a low limit is highly impractical and would result in a large number of false positives.

Intrusion Detection Group     

Goal

Set up effective IDS to detect and log covert scans from Alpha Team.

Members

    "yourbases"   William Strathearn   bill@cs.ucsb.edu  

Mission

Setup and deployment of one or more Intrusion Detection Systems tuned to detect and report on the port scans and fingerprinting traffic sent by the Alpha Team. Experiment and modify base installation to better detect random multi-host to multi-host port scans.If necessary, offline analysis of tcpdump files collected to discover more fine-grained attacks. All attacks discovered were to be automatically logged in IDMEF XML format without human intervention.

Preparation

Many Intrusion detection systems were downloaded installed and tested for thier ability to effectivly detect the scans launched during this exercise. The IDS's choosen were then installed and the configurations fine tuned to detect slow many to many port scans.

We choose Snort version 1.9.0 as our primary online IDS. Snort was primarly written by Marty Roesch., but has many other contributers and points of inspiration. Excess rules and other unecessary cruft were removed to provide for fast effecient setup and operation. New rules were found and donloaded from Whitehat

For offline analysis of smaller tcpdump files, NetSTAT was choosen as a more effective means of detected attacks requiring statefull analysis. NetSTAT was written by the Reliable Software Group at the University of California, Santa Barbara.

In order to provide IDMEF alert messgaes without hours of manual labor, a perlscript was developed that converted the scans reported in the scan.log file created by SNORT into full IDMEF XML format alerts. Scan.log files have scans it deams similar, tagged with a unique ID. The perl script written goes through each scanned port for each unique ID and collects a list of sources of the attack, target hosts and target ports. It then builds an attack alert for each unique ID. The attack is profiled and described based on the IP flags of the packets recieved. A TCP filter is then built so that effective extraction of the attack from a large TCP dump file may be peformed. Log converter was written by William Strathearn (yourbases) and can be found at: cs.ucsb.edu/bill/courses/cmps279/scanLog2IDMEF/

Execution

During the setup of the exercise, "yourbases" downloaded and installed the IDS's choosen, and used pre-modified configuration files for ease of setup. An xterm to monitor alerts as they were reported was set up. This allowed the team to monitor the activity of Alpha team and report on thier progress as the alerts were reported. Omega team could then adjust it's strategy based on the progress of the other team.

During the execution of the exercise, the realtime alerts were examined and reported upon to the the other team members.

After the execution of the exercise, the IDMEF messages were collected and put into a detection summary. Offline analysis of the logs were planned, but the offline analysis tool (NetSTAT), was installed only on our attack machine which was made unavailable after the close of the attack.

Evaluation

The plan of detection was executed without a hitch. However, more extensive testing should have been performed to allow the detection of slower attacks. Although the default settings in the IDS were modified, I have a feeling that the Alpha team indeed scanned more than 100 ports on each of our live machines. Also, Netstat should have been installed on a local cs account so that the attack machine was not relied upon after the exercise was over. However, as a critisism of the exercise itself, it was not known in advance that the analysis would have to be performed on our local accounts.

Also, more time should have been allocated to write the scan.log converter. Despite the fact that it works very well, I did not have time to implement an NTP time converter.

Miscellaneous

Some of my responsibilites in this group were light, as a significant amount of time was spent organizing, and leading the Omega Team.

Scan Confuser Group - A     

Goal

The subgroup developed a confuser which acts as a virtual machine. This confuser can be used as a defense to counter various scans and attacks. Its basic idea is to show -> DOWN hosts as UP and CLOSED ports as OPEN.

Members

    "topgun"   Nisheeth Shrivastava   nisheeth@cs.ucsb.edu  
    "adythemaddy"   Aditya Thyagarajan   adityat@cs.ucsb.edu  

Mission

As part of defense, our mission was to make the confuser work for as many port scans as possible. The confuser works for all (except OS finger printing) nmap port scan options. It also works for pingscan and telnet. We also had an automated perl script running to check for port scans against the confuser. The confuser replies OPEN only for a subset of common open ports on machines. Eg: port 80. The confuser works for TCP Connect scan, TCP Syn Scan, TCP FIN, Null and XMas Scans, UDP scan, Ack Scan, RPC Scan and Ping scans. We also implemented the TCP Ping Scan (-PT option) where Ack packets are spewed throughout the network to attack target hosts and monitor their responses. The confuser also helped TCP/UDP attack teams by providing them with arp-replies for their spoofed attacks.

Scan Confuser Group - B     

Goal

Write a Scan Confuser to deter OS Fingerprinting and Port scans.

Members

    "blitzkrieg"   Vineet Thanedar   vineet@cs.ucsb.edu  
    "sepultura"   Amit Jardosh   amitj@cs.ucsb.edu  
    "protector"   Saranyan Rajagopalan   saranvr@cs.ucsb.edu  

Mission

To write a Scan Confuser that detects scans like NULL scan, FIN scan, XMAS scan & ACK scan and sends replies which would confuse the opposite team without any violation of the exercise rules. The primary motive of the Confuser is to thwart OS fingerprinting attempts done by using the above scans.

Preparation

The preparation for the Scan Confuser included the following tasks:

  • Understand Concerned scans.

    Since the primary task of our subgroup was to thwart OS fingerprinting attacks by the Alpha team, we concentrated on those scans which are typically used for OS fingerprinting, e.g. NULL, XMAS, FIN scans. We then studied the packet format and various flags associated with these scans.

  • Determine replies to be sent.

    The next step was to determine a suitable reply to these scans so that the opposition team can be confused. For eg. for an XMAS scan, linux responds by dropping the packet on an open port, whereas a windows machine sends a RST. This kind of a reply can be used to determine the OS of the target machine. We designed our ScanConfuser to send RST packets no matter what the target OS is. This gives wrong information to the opposition team.

  • Packet Capturing.

    The basis for the entire work is to capture the packets from the network. We used the 'libpcap' library to do this. Each packet is sniffed from the network and immediately processed for determining any possible scans.

  • Reading IP File.

    The ScanConfuser had an option of reading the IP addresses on the Omega Team subnet for whom replies were to be sent. This file was to be supplied by the team before the execution of the ScanConfuser.

  • Packet injecting.

    After determining the reply, the next task is to send it to the attacker. We used the 'libnet' library to inject the reply packets into the network. Appropriate flags were set in the reply packets sent. Also, we trie to optimize the code to make sure that our replies reach earlier than the system's replies.

  • Packet Logging.

    The ScanConfuser displayed the logs of the 'attack' packets that have been sent to our subnet and the replies that the ScanConfuser sent as a response

Execution

During the first half of the exercise a ScanConfuser developed by the Omega team was used. The Scan Confuser we wrote was to be used in the latter half of the exercise so that the opposition gets a different set of replies and thus would not be able to infer much from their attacks. However, during the exercise, the entire team decided to use ScanConfuser as the team strategy was working as planned and was giving positive results.

During the exercise our team was involved with analysis of the dumps and carrying out Banner Grabbing functionalities for a set of ports on a set of IP addresses.

Evalutation

We have tested our ScanConfuser against all the intended scans and the ScanConfuser sent replies. We used the NMAP tool to generate scans with different options.

Miscellaneous

Each member of the group contributed equally. We divided work amongst ourselves and finally integrated the individual programs. The tool that has been developed by our group is ScanConfuser
