Mission:

Group D's mission was to do host-based intrusion detection on the Omega team's two hosts. In particular, monitor any remote to local intrusions, any modifications to system configuration files or binaries, and any attempt to access the real and fake flag files.

The group members responsibilities were:

Fredrik: Kernel level audit stream provider and a simple IDS based on this audit stream.
Vladimir: Procfile monitor. Develop an IDS using observed changes in the proc filesystem as input.
Arun and Mohit: IDS for monitoring critical system files and log files. Used a tool called fcheck that monitors when specified fails have been changed etc. Another tool called file_monitor was use to log changes to critical system files and to monitor suspicious messages in the system log file.
 

Preparation:

Most of the software used by the group was developed by the members. The following software components were used:

kaudit: A kernel level audit provider. The system has two parts, a kernel module that records events and sends them to user-space and a user-space daemon that reads the events, matches them with a number of rules and logs any attacks found to a file. The system audits all open() and execve() system calls. The IDS rules detects opening of any file named 'secret.txt', daemons executing a shell, opening of files in /bin, /sbin or /etc for writing, execution of a unknown suid program, and the bobek ftpd attack. The program was developed by Fredrik.

daemonstalker: user level program for monitoring daemons via /proc directory. To monitor /proc directory Vladimir used Linux Performance Monitoring Library (http://www.olny.cz/linux_monitor/). Using this library Vladimir was able to detect processes creation and their behavior. Specifically Vladimir was able to monitor shells which do not have tty attached. Shell would not have tty attached if it spawned by a daemon or if there was a buffer overflow against the daemon followed by execve(sh). That is, software mainly monitored shells which do not have tty attached and used to be daemons.

fcheck: fcheck is a free software, distributed under the GNU GPL. Essentially, FCheck has the ability to monitor directories, files or complete filesystems for any additions, deletions, and modifications. It is configurable to exclude active log files, and can be ran as often as needed from the command line or cron making it extremely difficult to circumvent. The tool maintains a database with all the information that it needs to monitor. This database needs to be initialized and then every time fcheck is run, it compares the current state with the database. For the Red-Blue exercise Arun and Mohit configured fcheck to monitor /etc, /var/log, /root/.ssh

file_monitor: This is a tool developed by Arun and Mohit to monitor any changes to log files and other important files during the attack. The changes seen are logged into a log file. The files monitored during the exercise include /etc/passwd, /root/.rhosts, /.ssh/authorized_keys, /var/log/messages. This gives important information such as whether any new user has been created etc. The messages logged in /var/log/messages are scanned to look for those that may have resulted out of a buffer overflow attack, wuFTP attack etc. All suspicious messages are logged into a log file maintained by file_monitor.

Evaluation:

The group was able to give real-time feedback about the Alpha teams activities. The IDSes used were able to detect which attacks were successful, information that usually is not given by a network based IDS. The group was also able to monitor how the search for the flag file progressed and if the real flag file was found. Most of the groups work was completed during the preparation phase. During the attack we just monitored the IDS logs and shouted out every time we saw any signs of attacks. This information was non-essential for the other groups work, but helped us create a view of how Alpha's attack was progressing. All the tools used worked as they were supposed to, and we were able to detect the break-ins into both hosts. A possible improvement would have been to extend the signatures of kaudit and daemonstalker so that both detects the ftpd and lpd attacks that were used by Alpha.

As an overall evaluation of the exercise, too much time and effort was spent on hiding and searching for the flags. In a real world scenario the break-in process is the most important. Creating and searching a highly corrupted and obfuscated filesystem is less of an issue.
