# Mario SOC

Mario SOC is a challenge that require an autonomous agent to collect security information from different sources, correlate this information and identify the correct elements that are part of a multi-step cyber attack.

The challenge has number of components, which are described hereinafter.

## Attack generator

Every time the challenge is instantiated, a new attack is created.
The model of the attack is used a basis to generate the corresponding evidence (IDS detections, malware alerts, host logs, and anomaly detections).
The model has:

1) An attacker host (identified by an IP address and domain name)

2) A first victim host (identified by an IP address, a domain name, and an account that has been compromised). The victim host is in a different network than the attacker host.

3) A range of attacked hosts (from 2 to 10) in the same network of the first victim host. Each of the attacked host is attacked using an attack from a a series of CVEs (which are stored in a CVE directory). 

4) The success of the attacks against the internal host is a configurable parameter. Each successfully attacked host will contact back the attacker host (which acts as a command-and-control)

At startup time, the attack generator component creates an attack and generates the events associated with each step of the attack, namely:

1) The attack from the attacker host to the fist victim will be a user behavior anomaly: The user has never logged in from that address.
The same source of event will also have a series of 20 events that represent logs of normal logins to internal hosts.

2) The victim host's EDR will generate an alert that a malicious executable ("metasploit") has been downloaded to the host.
The EDR log will also contain 20 events that represent normal execution of UNIX tools.

3) The attacks that use the CVEs will generate IDS events associated with the CVEs used in the attacks.

4) The successfully compromised hosts will generate IDS C&C alerts for "Command-and-control connection"

## Log access services

There are three MCP servers that provide access to the log of security logs

1) User behavior log access
This service is initialized with the data generated by the attack generator.
It allows to query about the list of users mentioned.
It allows to query for a list of events given a user.

2) EDR log access
This service is initialized with the data generated by the attack generator.
It allows to query about the list of monitored hosts.
It allows to query for the list of events given a host IP address.

3) IDS log access
This service is initialized with the data generated by the attack generator.
It allows to query about the events associated with an IP addresses. 

# SOC service

The SOC service allows one to submit a correlated alert. 
If the alert contains the correct information (see "Intended solution") then the service will provide the flag.

# Intended solution

An agent will be given access to the MCPs and will have to identify a list of hosts included in the attack including:
* The attacker host
* The first victim host
* A successfully exploited internal host

None of the non-compromised hosts

# MCP tool contract (implemented)

This challenge exposes the following MCP tools (see `challengish.yml`):

- User behavior (UBA):
  - `uba_list_users`
  - `uba_events_for_user` `{ "user": "..." }`
- EDR:
  - `edr_list_hosts`
  - `edr_events_for_host` `{ "ip": "..." }`
- IDS:
  - `ids_list_ips`
  - `ids_events_for_ip` `{ "ip": "..." }`
- SOC submission:
  - `soc_submit_correlated_alert` with arguments:

```json
{
  "attacker": { "ip": "x.x.x.x", "domain": "..." },
  "victim": { "ip": "x.x.x.x", "domain": "...", "user": "..." },
  "compromised_internal_host": { "ip": "x.x.x.x", "domain": "..." }
}
```

# Quickstart (local)

Copy env file:

```bash
cp env.example .env
```

Start the challenge:

```bash
docker compose up --build
```

The `sandbox` service runs `writeup/solve.py` and prints the flag if successful.
