1. INTRODUCTION
   
   The objective of  Spam Delivery Protocol (SPADEP) is  to allow user to send
   spam messages in a reliable, efficient and authenticated way.

   SPADEP is independent of the particular transmission subsystem and requires
   only a reliable ordered data stream channel.

   An  important feature of  SPADEP is   its capability  to relay  mail across
   transport  service  environments.   A   transport    service  provides   an
   interprocess  communication environment  (IPCE).    An IPCE  may  cover one
   network, several networks, or a  subset of a  network.  It is important  to
   realize that transport systems (or IPCEs) are not one-to-one with networks.
   A  process can   communicate  directly with   another  process through  any
   mutually known IPCE.   Mail   is an  application  or use   of  interprocess
   communication.  Mail  can  be communicated  between  processes in different
   IPCEs by relaying through a process connected to two (or more) IPCEs.  More
   specifically,  mail can be relayed  between  hosts  on different  transport
   systems by a host on both transport systems.

   Commands  in  the SPADEP consist  of   a case-insensitive keyword, possibly
   followed by one or more  arguments.  All commands  are terminated by a CRLF
   pair.  Keywords  and  arguments  consist   of printable  ASCII  characters.
   Keywords and arguments are each separated by a single SPACE character.

2. THE SPADEP PROCEDURE

  There  are  four steps  to  SPADEP mail transactions. First   of  all, it is
  necessary to  login into  the system using   a valid userid and password  or
  create a new  account on the spam  server.  Then, the transaction is started
  with a FROM  command which gives the  sender  identification.  A  TO command
  follows, giving the  receivers' information. Then  a SPAM command gives  the
  mail  data.  And   finally, the end   of  mail data  indicator  confirms the
  transaction.

   2.1 AUTHENTICATION
          
         The  client must now identify  and authenticate  itself to the SPADEP
         server. Two possible mechanisms for doing  this are described in this
         document, Login with  a previous account or create  a new  account on
         the fly.

           C: login foobar secret
           S: 200 OK

         When the client issues the LOGIN  command, the SPADEP server uses the
         two arguments  to determine if the client  should  be given access to
         the spam service.

   2.2 CREATION OF A NEW ACCOUNT
        
         If the user does not already own an account,  he/she can create a new
         one using the NEW command.

           C: new foobar supersecret
           S: 200 OK
       
         The server should not accept two user accounts with the same username
         and should check the password  in order to prevent some easy-to-guess
         dictionary words.

   2.3 SENDING SPAM
   
         After the user is authenticated into the system, the next step is the
         FROM command. The <reverse-path> contains the source mailbox.

            FROM: <SP> <reverse-path> <LF>

         This command  tells the SMTP-receiver that  a new mail transaction is
         starting. It gives   the reverse-path which  can  be used  to  report
         errors. If accepted,the receiver-SMTP returns a 200 OK reply.

         The  <reverse-path> can   contain  more than just   a  mailbox.   The
         <reverse-path> is  a reverse source routing  list of hosts and source
         mailbox.  The  first host in  the <reverse-path>  should be  the host
         sending this command.

         The second step in the procedure is the TO command.

            TO: <SP> <forward-path> <LF>

         This command  gives  a forward-path  identifying  one recipient.   If
         accepted,  the receiver-SMTP returns a 200  OK  reply, and stores the
         forward-path.

         The   <forward-path> can  contain more than   just   a mailbox.   The
         <forward-path> is a source routing  list of hosts and the destination
         mailbox.  The  first host in the  <forward-path>  should be  the host
         receiving this command.  If a user want to  send a message to all the
         other users of the current server, it is  possible to specify "local"
         as forward recipient. In  such a case,  the server is  responsible to
         put all the local account name in the <forward-path>

         The third step in the procedure is the SPAM command.

            SPAM <LF>

         If accepted,  the  receiver-SMTP  returns an intermediate   reply and
         considers  all succeeding lines to   be the message  text.  The first
         line of the message will be considered as the message header.
        
         When the end of text is received and stored the SMTP-receiver
         sends a 200 OK reply.

         Since the mail data  is sent on the  transmission channel the  end of
         the mail data must be indicated so that the  command and reply dialog
         can be resumed.  SMTP indicates the end of the mail data by sending a
         line containing only a period.

         The end of mail data indicator also confirms the mail transaction and
         tells the receiver-SMTP to now process the stored recipients and mail
         data.  If  accepted, the receiver-SMTP returns  a 200 OK  reply.  The
         DATA command should fail only if the  mail transaction was incomplete
         (for example, no recipients), or if resources are not available.

      The above procedure is an example of a mail transaction. The FROM and TO
      command can be used in any order but always before th SPAM command.

   2.4 OTHER COMMANDS

      All the SPADEP server must implement the following commands:
        HELP
        WHOAMI
        STAT
        EXIT
     
     The HELP command must  provide a useful information  to any user, listing
     all the commands supported by the server followed by a short description.
     The WHOAMI command can be used to print the username currently associated
     by the user. EXIT is the right way to close a connection with the server.

     The STAT command can be used  to list the mails  that for some reason are
     still into the sending  queue. Every time a new  spam is accepted by  the
     server, the message  is  put into  a queue, waiting  to  be sent to   the
     destination. The stat command print the header of all the messages in the
     user queue.

3. EXAMPLES


     -------------------------------------------------------------

                     Example of the SPADEP Procedure

         This SPADEP example shows spam sent  by nobody@nowhere.com, to Jones,
         Green, and Brown  at host Beta.ARPA.  Here we  assume that host Alpha
         contacts host Beta directly.

            C: LOGIN badguy secretpassword
            S: 200 OK

            C: FROM: nobody@nowhere.com
            S: 200 OK

            C: TO: <Jones@Beta.ARPA>, <Green@Beta.ARPA>, <Brown@Beta.ARPA>
            S: 200 OK

            C: SPAM
            S: - Write your spam message here.
            S: - The first line must be the subject
            S: - A line containing only a comma (.) will end the message
            C: Super super cool 
            C: ...etc. etc. etc.
            C: <CR>.<CR>
            S: 200 OK

         The mail has now been accepted and put in the sending queue.


            C: stat
            S: Mail currently in the sending queue:
            S: 1 - Super super cool
            S: 200 OK
