OUR MISSION:

The mission of our group was to scan the targeted systems remotely and get
possible security holes in these machines. The idea is to get the
information pertaining to these remote hosts (IP, OS, etc) from group 1
and conduct a thorough vulnerability scan that could be later exploited by
the next group that is Vulnerability Exploit group. So we had to pass our
scan reports to the exploits group thus helping them run the right
exploits on those machines. We also had an interface to the group 2
i.e. Service Scan group and they provided us with some scripts to parse
host information collected by group 1.

This is how we had our responsibilities divided among the group members.

PREPARATION:

Our main tool for detecting vulnerabilities was Nessus in which we used
the Plugins corresponding to the exploits collected by the later
groups. Sara was another useful tool for vulnerability detection and
analysis that we planned to used during the exercise.

Our first duties as a team involved finding out about Network
vulnerability scanning, what it is and how it's done, etc. We also
required various tools that do the remote scanning like Nessus, SARA,
SAINT, etc. These were initially looked for on the Internet and studied
for pros and cons. 

We finally narrowed down on NESSUS and SARA (SATAN was considered
too). However, we ultimately went for NESSUS due to its neat client/server
architecture and its ability to do an extensive scan using loads of
Plugins stored in its Knowledge Base. Also, NESSUS runs NMAP tool before
its scan and so provides a service scan report too (task of group 2 done
here). 
For interfacing with the Exploit group we needed to provide them with a
scan report for their collection of exploits. In anticipation of that,
Siddharth wrote a shell script (that uses awk) which takes as input the
NESSUS generated report (which we must say is quite exhaustive) and
generates a nice little report with only the information relevant to the
Exploit group. This includes the OS and IP addresses information (provide
by the group 1) followed by our scan report which provides security holes
found on the targeted machines and some very useful service information.

For better performance during the actual scan we made sure that we run the
NESSUS tool in the most optimized way. That included narrowing down the
scans to important vulnerabilities and those, which were collected by the
later group to exploit. Also, we decided to separately run different
Nessus clients for scanning Linux, Solaris and NT machines (if any) on
separate servers. This way we saved time on scanning the Linux machines,
which were our main targets during the attack.

Installation of the server part of Nessus was carried out on the testbed
network and tested and practiced on (running on altman). The client
portion of Nessus facilitated connectivity to the server Nessus
daemon. Our members ran a complete scan on the testbed network computers
and got familiar with the internals of the tool especially the various
options that could be set to target machines with specific
characteristics.
As our group leader, Siddharth held several meetings with both our group
members and also leaders of adjacent groups as we realized that the
success of this exercise highly depended on how properly we are interfaced
to other groups. This helped us figure out exploits for vulnerability
scanning and effectively lead our tasks. Tirth's duties as the interface
for our group involved corresponding with the interfaces of group 2
(Service scanning) and group 4 (Vulnerability Exploits). Qiang and Yongbo
took charge of the final installations of Nessus on the Red Team machine
under the supervision of Siddharth. Lin installed SARA on audit5 and
tested it on the testbed machines to try out if it would be some extra
help during the exercise.

EVALUATION:

	Nessus is a remote network security auditor, the client The Nessus
Security Scanner is a security auditing tool. It makes possible to test
security modules in an attempt to find vulnerable spots that should be 
fixed. It is made up of two parts: a server, and a client. The 
server/daemon, nessusd, is in charge of the attacks, whereas the client,
nessus, interferes with the user through nice X11/GTK+ interface. . This
package contains the GTK+ 1.2 client, which exists in other forms and on
other platforms, too. 

The Security Auditor's Research Assistant (SARA) is a third generation
security analysis tool that is based on the SATAN model which is covered
by the GNU GPL-like open license. It is fostering a collaborative
environment and is updated periodically to address latest threats. SARA
doesn't need the OS type before vuln. scan as it can enable nmap by
-n. And it also has data analysis and reportwriter. So this tool is very
flexible.

	Using these kinds of tool was a very new and good experience
especially in such a nice team exercise. However, we did learn that its
not always good to rely on such tools as results from today's exercise
points out to. Instead, there must always be some manual backup scans for
getting the task done cleanly. However, since we found it difficult to
figure out how scans scripts can be developed without actually exploiting
the targets for those particular scans. So, we feel there's a really fine
line here. Still, more dependable scanning tools can be worked on.
