Mission

This sub-group of the red team was responsible for escalation to root after they had been given a user account on the attacked machine. The group before this (vulnerability exploit) was responsible for providing us with a user account. We were then supposed to run the exploits we had and get a shell with root privileges which we used to execute the next group's scripts for flag acquisition.

  The splitting of the work was thought to be even among the group members. Each member of the group found at least one or two working exploits from the ones that were collected, documented them, built the script to execute them and wrote part of the documentation. Some members tried extra things such as password cracking, or exploits for other non-Linux maxhines. The group leader had some extra tasks apart from the normal member responsabilities, and wants to state that everybody responded promptly and pretty efficiently on the tasks that were assigned. Everybody helped in the excercise execution.

Preparation

Each member in the group had the initial task of collecting exploits, study them, understand them and then run them on the testbed to see if they worked. Some of them were based on buffer overflows so they had to be tested with various offsets to see with which ones did they work with.

 Once we had several working exploits in our repository, we split them and each member provided:

  • a script to run the exploit, which included any kind of compilation, tool checking and offset testing ,which returned a non-zero value in the case of failure or a root shell otherwise. Some solaris exploits were to be pre-compiled for the appropriate architecture since no gcc was available on the target machine.
  • a readme file to highlight the uniqueness of the exploit, like the vulnerability that it exploited, the machine and the OS that it was meant for and any other specific details under which it worked or it failed.
Thus we built up a common repository repository of exploits each with the source, binary, readme and the script.  The repository was also used as a synchronization tool to avoid more than one people to work on the same exploits, optimizing their search.

 A metascript was also built, which was able to automatically detect the type of operating system and systematically try the available matching exploits for it. The script used the non-zero returned values to keep trying more scripts in the list.

  The result of building such  repository of documented exploits with their own individual scripts along with the metascript, allowed our group to completely automate the break-in process given a user shell.

Some team members tried password cracking (using John the Ripper) so our team could try to break into a machine which couldn't be compromised by the remote exploits team. This actually turned up to be very effective on the solaris machine (see execution).

  Another important task was the communication/synchronization with the other groups:

  Our interface to the previous group was very simple: We would provide them with a tar file which contained all the necessary scripts and binary programs to carry out escalation to root privileges plus the flag acquisition. To automate the process, the remote vulnerabilities team only had to transfer the file into the user account broken into and type:

   tar xf XMEN.tar ;  ./escalate.sh

The interface to the group for flag acquisition provided us with a perl script which had to be run with root privileges. Our escalate shell script would present a root shell in which the only manual intervention needed was to type "../flag.pl" in order to trigger the flag acquisition program. We didn't think that modifying our eggshells to automatically run the flag script was necessary.
 

Execution

  Since the remote exploits of the group before us were able to get root privileges directly on the linux RedHat6.2 boxes, our scripts were not needed in those situations. However, since there were no remote exploits for solaris, we used one of the cracked passwords from one of the linux machines to log in to goddard (the solaris box). Once there with user privileges, we needed to get our tar file with our exploits. Since the solaris machine was "bare-bones" installed, we couldn't use scp, rcp utilities, and we of course didn't want to retrieve the file from our cs accounts with ftp (password in the clear with half the other class sniffing the network). Since the machines we had prepared for the attack didn't have the ftpd setup either, we decided to retrieve our scripts through one of the back door users in the already broken into linux machine (in that case doesn't matter to expose the password with ftp ).

 Once we had our exploits, we just ran: tar xf XMEN.tar; ./escalate.sh and we immediately got a root shell.

 Then we tried to execute the flag acquisition program but the machine didn't have perl installed, so we had to manually search for the flag. That machine didn't have any flag file. A remotely mounted nfs directory from leone (which was down) complicated a bit the search since it was mounted with  the"hard" option and it was not even possible to unmount it.

Evaluation

How well the subgroup accomplished its mission:

Our scripts were supposed to be automatically executed from the team before us. Since the group could get root privileges remotely they didn't have the need to execute our escalation. Our automated scripts we were able to always break in  any of the test-bed machines before the excercise. So our overall evaluation is that our work was solid and consistent.

However,  since the remote vulnerability group concentrated in the linux boxes (the only official targets), we could successfully test our automated scripts in a solaris machine. We got user acces from a cracked password in one of the linux machines. Again, our script showed to be consistently working for solaris.

How well the subgroup executed the plan of attack:

Our subgroup was successful in finding exploits that gave root access. We had eight working local working exploits, six of these were for RedHat 6.2 and two for Solaris. In addition to this, we had two remote root exploits as well, which we didn't use to avoid overlap with another group.

A description of what could have been done better:

We focussed mainly on only two platforms, namely Red Hat 6.20 (some 7.0) and Solaris.
We could have also done some home work for Windows NT.
Finally, to completely automate the process, we could have changed the root shells on the eggs, or changed the program to "setuid", in order to execute the flag acquisition script without needing to type "../flag.sh". That was a considerable amount of work compared to the amount of typing overhead (just 4-6 machines).

How well the subgroup interacted with any adjacent subgroups:

  As explained before, we designed the interfaces with the other groups to be very simple and provide automatic execution.

  We provided a tar file (XMEN.tar) to the group before us which only needed to be untarred and execute "./escalate".

  Our tar file always contained the flag acquisition program (we received from the group after us) which was manually executed after a successful exploit.

The tools that were available for performing the subgroup's mission:

A number of exploits are available on the Internet for escalating user access to privileges. But only a few of them actually worked as claimed. We found it difficult to read the exploit code and try and figure out why a particular exploit wouldn't work. This was so because the exploit code available on the Internet is not really well documented. Comments and/or readme files that explained the nature of the bug and how the author of code was attempting to exploit it would have helped.

In some other cases, the vulnerability had simply been patched though the author of the exploit claimed that they worked.  Eg. mogrify is a program that contains a buffer overflow. The exploit code available for this claimed to work even on RedHat 7.0 But we found (both on the test bed and on a RH 7 box) that the executable is not setuid root. (It was not much fun, getting our own shell).

Of the password cracking tools available on the Internet, we were successful in using John the Ripper on the testbed. We made sure we were able to run this tool on a Linux box just in case we needed to do some password cracking on the day of the exercise. (No we did not expect the root password to be easily crackable, but thought it could be useful since many users could share passwords accross machines). We think that this is pretty neat tool, because we had no difficulty in getting this to work.

An evaluation of the exercise itself:

The exercise helped in understanding how easy a network can be compromised by malicious hackers using freely available tools. This is an important first step in being able to "secure" a network against attacks. Another of the learned things is that fully automating these kind of attacks are not easy, let alone doing it in a "stealth" mode.

Probably and improvement for the excercise would be to give everybody the opportunity to be in both teams (i.e two rounds) so they can get the experience from both sides. However, with a class this size(60+?) and a quarter only so long(10 little weeks) this is might not be within limits of possibility.
