Mission

The Service Scanning Group (SSG) is responsible for quickly and effectively identifying the available network services on all of the attacked hosts. The end product of our phase of the Red Team attack will be a concise and well-formatted listing of both TCP- and UDP-based services running on each host as well as the ports on which the services are listening. We will be provided with a list of IP addresses for the target hosts from the OS/Topology Group. This list will be piped through SSG automated script(s), which will execute the service scan and report the results in a form that facilitates the needs of the Vulnerability Discovery Group.

Preparation

After researching various tools and deliberating amongst ourselves, we concluded that nmap is the best tool for our purposes. It provides an elegant and simple interface to various port scanning methods, including those that are least detectable by intrusion detection software (i.e., Christmas Tree Scan, Fin Scan). We also strongly considered nessus, but decided that it had more functionality than was necessary for our needs.

Late into the quarter, it was determined that the Vulnerability Discovery Group would subsume our work since they chose to use nessus which internally runs nmap. Therefore, an explicit interface between our groups was not necessary. Our group chose to continue developing a separate script to run nmap based on the input from the OS/Topology Group as a backup in case nessus failed to scan properly. In addition, we discussed appropriate nmap settings within nessus with the Vulnerability Group and wrote two parsing scripts which translated the interface files from the OS/Topology Group to something usable by the Vulnerability Group. In total, the group produced three scripts:

red.iplist
This script transforms a list of ethernet, ip, os tuples into a simple list of ips.
red.ossplit
This script transforms a list of ethernet, ip, os tuples into a set of ip lists separated by os type. Files names IP_{os} are generated for each recognized os, and a separate IP_Unknown is created with all ips from unrecognized operating systems.
red.pscan
This script runs nmap with options to Xmas and UDP scan a list of targets. The list can be specified as a combination of command-line ips, a file with white-space separated ips or in an interface file containing a list of ethernet, ip, os tuples.

Looking beyond nessus and nmap, the group also investigated other possible tools such as autonoc, blackice, rnamp and zapatista.

Evaluation

Our group was successful in its mission, although that mission changed to some degree through the quarter. Considering that our fate became rather intimately intertwined with the Vulnerability Discovery Group, service scanning was as effective as it could be. Our interface parsing scripts were not used as fully as expected since the OS/Topology group began to pass information by hand rather than in the agreed upon electronic format. We did run a separate service scan using our own scripts, and they were useful in discerning which reported IP addresses were valid hosts.

Our group interacted well with the two adjacent groups, OS/Topology and Vulnerability, both before and during the exercise. Furthermore, once the scanning was complete, all of our group members helped to determine missing information about certain hosts such as OS type, as well as, help to distinguish between real and spoofed hosts. Once all machines were successfully identified, our group helped in the exploit effort by trying to leverage trust relationships between compromised hosts and other uncompromised machines.

If we were to hold the exercise again, a few things could be improved. Although Dan did a good job of coordinating efforts, there was considerable overlap as the exercise progressed. It would have been better if there had been a whiteboard or some central point where progress was monitored for each target host. Also, the fact that Leone changed IP addresses mid-exercise was not quite fair. We actually made a point to continually revisit Leone (.20) to see if it was back on-line, and it wasn't until quite late into the exercise that we learned it had come back up as .21.

The exercise actually progressed better than expected. It seemed that most groups were prepared. Even when automated scripts began to break down, the group members were able to diagnose the problems and either fix the broken scripts or continue by hand. Throughout the exercise, most people were helping outside their own group, assisting other groups where needed. Dan did a very good job of coordinating the efforts and maintaining some semblance of order.
