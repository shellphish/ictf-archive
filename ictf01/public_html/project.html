CS 290I Network Security and Intrusion Detection - Project

The final for the class consists in a project.

The project can be of two types:

  • A vulnerability collection (deadline March 17th, 2001 at midnight)
  • The implementation of a new attack or the development of some security-related application (deadline March 18th, 2001 at midnight)

Projects can be carried out in groups. Groups can be at most of three people.

Both projects can provide up to 12 points. These points will count for 50% of the final grade.

Note that the project points are not in scale with the homeworks or red team/ blue team exercise.

Some of the best projects will be presented March 19, 2001 from 12 to 3pm.

Vulnerability Collection

The vulnerability collection project consists in analyzing several vulnerabilities and the corresponding exploits.

A minimum of 4 vulnerabilities must be submitted.

A maximum of 5 vulnerabilities can be submitted. Submitting 5 vulnerabilities can help in reaching (but not in overcoming) the maximum score (12 points).

Each vulnerability will be evaluated with a score from 0 to 3.

If the project is carried out in a group, the number of vulnerabilities to be submitted will grow linearly with the number of people in the group. For example, a group of three people must submit a minimum of 12 vulnerabilities (and may submit a maximum of 15 vulnerabilities).

Requesting a Vulnerability

Each vulnerability must be approved by the instructor, before submission. This is to avoid multiple submissions for the same vulnerability. To get a vulnerability approved it is necessary to send an email to vigna@cs.ucsb.edu with the following data:

  • Subject: last,first CS290I_Vulnerability Request
  • Body:
    <vulnerability>
      <group>
        <student>Last1,First1</student>
        <student>Last2,First2</student>
      </group>
      <name>Name of the vulnerability, if well-known</name>
      <bugtraqid>bugtraq id, if available</bugtraqid>
      <description>Brief description of the vulnerability</description>
    </vulnerability>

For example, suppose that students Mark Twain and Bill Shakespeare want to include the phf vulnerability in their vulnerability collection. Mark and Bill decided that Mark Twain is the "point-of-contact" (POC) for the group. Therefore, Mark sends the following message to vigna@cs.ucsb.edu:

Subject: Twain,Mark CS290I_Vulnerability Request

<vulnerability>
  <group>
    <student>Twain,Mark</student>
    <student>Shakespeare,Bill</student>
  </group>
  <name>phf (exec)</name>
  <bugtraqid>629</bugtraqid>
  <description>phf CGI script allows one to execute arbitrary commands</description>
</vulnerability>

If the vulnerability is accepted, you can start collecting the necessary information.

Submitting a Vulnerability Collection

To submit a vulnerability collection, you have to send a separate message for each vulnerability. To submit a vulnerability send an email to vigna@cs.ucsb.edu with the following subject:

Subject: last,first CS290I_Vulnerability Turnin n/total

Where last and first are the last and first name of the POC. n/total indicates what vulnerability is the one attached to the message. For example, if a group of three people whose POC is Mark Twain is submitting the third vulnerability of the thirteen they prepared, they would send a message with the following subject:

Subject: Mark,Twain CS290I_Vulnerability Turnin 3/13

Each message must contain, in attachment, a tar archive compressed with gzip. The name of the tar archive must be last_first_n_of_total_vulnerabilityname.tar.gz. Where last, first, n, total, have the meaning described above and vulnerabilityname is the name of the vulnerability (e.g., "phf"). The tar file must expand to a subdirectory that has the same name of the archive.

Each vulnerability must provide the following information

  • Name of the vulnerability
  • Discussion of the vulnerability
  • Vulnerable software (when applicable)
  • Exploit
  • Manifestation of the attack (and record of normal usage if possible)

Inside the archive there must be an index.html file containing the index to the contents of the directory. An example of the vulnerability archive for the phf directory is provided here. The packaged directory can be downloaded here.

The manifestation/signature information that must be provided for each vulnerability can be of two types.

If the attack is a "local" attack (e.g., a local buffer overflow) the manifestation is a trace of the system calls associated with the execution of the attack. The trace can be collected using the strace or truss programs. Here is an example:

    % strace -s 65535 -f -x -v -o buffer_overflow.trace ./vulnerable $EGG

In this case a buffer overflow in the program "vulnerable" is exploited. The trace of the execution (that is available here) shows the system calls invoked by the program, including the execution of /bin/sh as a consequence of the overwriting of the return address and execution of the shellcode.

If the attack is a "remote" attack then a tcpdump trace of the attack must be provided. See the phf vulnerability page for an example.

Note that a signature for the attack is not required anymore because there was not enough time spent in class on writing signatures to consider fair such a requirement. A discussion of how the attack manifests itself is required instead. For example in the case of the buffer overflow it would be enough to provide a comment on the fact that the execve system call is invoked as a consequence of the buffer overflow.

Security Application

This project must be discussed with the instructor and receive approval.

If the project is approved, a short description of the project must be sent by email to vigna@cs.ucsb.edu. The email message must contain the following data:

  • Subject: last,first CS290I_Project Description
  • Body:
    <project>
      <group>
        <student>Last1,First1</student>
        <student>Last2,First2</student>
      </group>
      <name>Name of the project</name>
      <description>Brief description of the project</description>
    </project>

For example, suppose that students Jim Joyce and Jack Kerouac want to propose a project on the security analysis of the RIP protocol. After having discussed the project with the instructor Jim and Jack decided that Jim is the "point-of-contact" for the group. Therefore, Jim sends the following message to vigna@cs.ucsb.edu:

Subject: Joyce,Jim CS290I_Project Description

<project>
  <group>
    <student>Joyce,Jim</student>
    <student>Kerouac,Jack</student>
  </group>
  <name>Exploiting RIP attacks</name>
  <description>
               The project will analyze the security of the RIP protocol and
               develop an attack that allows one to modify the routing tables
               of a network through a graphical interface.
  </description>
</project>

Submitting a Project

To submit the final project, you have to send a message to vigna@cs.ucsb.edu with the following subject:

Subject: last,first CS290I_Project Turnin

Where last,first are last and first name of the group POC.

The message must contain, in attachment, a tar archive compressed with gzip. The name of the tar archive must be last_first_projectname.tar.gz. Where last and first have the meaning described above and projectname is the name of the project (e.g., "totalrerouting"). The tar file must expand to a subdirectory that has the same name of the archive (i.e., last_first_projectname).

The archive will contain all the necessary information (including documentation) to evaluate the project.
